# RAG 进阶：改写、重排、评估

本文档记录三项优化的实现思路、实测数据和踩过的坑。

## 一、查询改写（Query Rewriting）

### 为什么需要

用户问「数据库怎么保证读性能」，文档里写的是「MySQL 主从架构，从库只读」。
这两句话字面和语义都对不上，直接检索必然失败。

实测重排分数：

| 查询 | 对「主从架构」片段的重排分 |
|---|---|
| 数据库怎么保证读性能 | 0.005 |
| 如何提升数据库读性能 | 0.005 |
| 数据库读性能优化 | 0.003 |
| **数据库主从架构** | **0.731** |
| **从库只读** | **0.650** |

结论：**必须改写出具体技术术语**，否则再好的重排也救不回来。

### 实现

`one/query_rewrite.py` 提供三层策略：

| 方式 | 耗时 | 触发条件 |
|---|---|---|
| 规则改写 | < 1ms | 口语词替换（咋→怎么、啥→什么） |
| LLM 改写 | 2-3s | 口语词、指代词、「怎么+动词」型问题 |
| 智能改写 | 按需 | 先判断 `needs_llm_rewrite()`，需要才调 LLM |

LLM 改写的关键在 prompt：

```
核心要求：必须使用具体的技术术语，而不是口语描述。
思考：这个问题在技术文档里通常怎么表述？对应的专业名词是什么？
```

实测效果：

```
数据库怎么保证读性能
  → ["数据库怎么保证读性能", "数据库主从架构 读写分离", "从库只读 主库写入"]

内存老是不够用是啥原因
  → ["内存老是不够用是啥原因", "内存泄漏 排查", "堆内存 OOM 原因"]
```

## 二、重排（Reranking）

### 原理

| 类型 | 做法 | 速度 | 精度 |
|---|---|---|---|
| Bi-encoder（向量检索） | query 和 doc 分别编码成向量，算余弦相似度 | 快（毫秒） | 中 |
| Cross-encoder（重排） | query 和 doc 拼一起送进模型，直接输出相关性 | 慢（百毫秒/条） | 高 |

所以标准做法是：**粗排召回 12 条 → 精排取前 4 条**。

### 实现要点

**1. 多查询重排取最大分**

对每个改写查询分别算重排分，取最大值：

```python
best_scores = [0.0] * len(candidates)
for q in queries:
    s = rerank_scores(q, passages)
    for k, sc in enumerate(s):
        if sc > best_scores[k]:
            best_scores[k] = sc
```

实测：原问题给 0.005 的片段，用「数据库主从架构」去问是 0.731。

**2. 阈值要用「相对 + 绝对」双条件**

这是踩过的坑：一开始用 `MIN_SCORE = 0.30`，结果 Recall 从 91.7% 掉到 75%。

原因：bge-reranker 对「短查询 vs 长片段」的打分普遍偏低，
正确片段可能只有 0.1~0.2，一刀切 0.3 会误杀。

改成：

```python
floor = max(MIN_SCORE, top1_score * REL_SCORE)   # 0.02 和 top1 的 15%
```

**3. 模型加载要懒加载**

首次加载 17 秒，之后每次推理 0.09 秒。必须全局缓存，否则每次请求都重新加载。

## 三、评估（Evaluation）

### 三个指标

| 指标 | 定义 | 说明 |
|---|---|---|
| **Recall@K** | 正确片段进入前 K 名的比例 | 检索有没有找到 |
| **MRR** | 正确片段排名的倒数均值 | 找到的排得够不够前 |
| **Answer Accuracy** | 回答是否覆盖关键事实 | 生成质量 |

### 评估集格式

`one/eval_data/cases.jsonl`，每行一条：

```json
{"question": "密钥多久换一次", "answer": "90天", "keywords": ["90 天", "轮换"], "doc": "数据安全.md"}
```

`keywords` 是判断依据，比字符串全等更鲁棒（"90天" 和 "90 天" 都算命中）。

### 实测数据

语料：7 个文档 / 22 个块
评估集：25 条

四组配置实测（25 条用例，7 文档 / 22 块）：

| 配置 | Recall@4 | MRR | 单次检索耗时 |
|---|---|---|---|
| 基线（纯向量） | 96.0% | 0.960 | 0.02s |
| + 重排 | 96.0% | 0.960 | 3.5s |
| + 改写 | 100.0% | 0.980 | 0.4s |
| **完整（改写+重排）** | **100.0%** | **1.000** | 6.2s |

关键发现：

1. **单独加重排没用**（96% → 96%），因为粗排就没召回正确片段，
   重排只能对已有候选排序，救不回来。
2. **单独加改写就够了**（96% → 100%），因为改写把口语问题映射到了文档术语。
3. **改写 + 重排才有 MRR 1.000**，即正确答案全部排第一。

所以顺序很重要：**先解决召回（改写），再优化排序（重排）**。
只做重排而不做改写，是很多人踩的坑。

代价：从 0.02s 涨到 6.2s。生产环境按场景选——
普通问答用基线，对准确率敏感的场景才开完整方案。

## 四、踩过的坑

### 坑 1：异常被静默吞掉

```python
except Exception:
    queries = [query]   # 悄悄回退，看不出错
```

这个写法让我排查了半小时：改写一直没生效，但没有任何报错。
真实原因是 `server.py` 里忘了 `from config import get_client`，
`NameError` 被 except 吞掉，直接回退到单条查询。

**教训**：debug 阶段让异常暴露出来，比如加 `traceback.print_exc()`。

### 坑 2：外部做规则改写会覆盖 LLM 改写

`rag_eval.evaluate()` 原来在调用 `kb.search()` 前自己做了规则改写，
把 query 替换成了改写后的值，导致 `search()` 内部拿到的不是原问题，
LLM 改写基于错误输入，效果全失。

**教训**：检索流程只应该有一个入口，不要在调用方重复做同一件事。

### 坑 3：旧进程占着端口

`server.py` 启动报 `[Errno 10048]`，但 `Get-CimInstance` 查不到进程。
用 `netstat -ano | findstr :8000` 才找到真实 PID。

**教训**：重启前先 `Get-Process python | Stop-Process -Force`。

### 坑 4：切分边界切断语义

第一版按字符数切分，导致块从句子中间开始（如"命中率目标为 85%"前面丢了主语）。
改成按「标题 + 句子」切分，重叠也按完整句子取。

## 六、还能怎么优化

按投入产出比排序：

| 优化点 | 预期收益 | 投入 |
|---|---|---|
| 语义分块（按段落主题切） | 中 | 中 |
| 混合检索加权调参（alpha） | 低 | 低 |
| 父文档检索（小块检索、大块返回） | 高 | 中 |
| 并发重排（多查询并行） | 中 | 低 |
| 改写结果缓存（已实现） | 中 | 已做 |
| 查询扩展（同义词、上位词） | 中 | 低 |
| 微调 reranker | 高 | 高 |
| 接入 RAGAS 自动生成评估集 | 中 | 低 |

最推荐**父文档检索**：检索时用小块（精准），返回时给大块（上下文完整），
这是目前工业界效果最好的改进之一。
